# Telegramvisor

Telegram communication for T3, independently of project and workflow supervision.

- Short recaps of substantial completed work, generated by Luna with max reasoning.
- Exact full answers to messages routed from Telegram.
- Input-needed notifications and native questionnaires with buttons or text replies.
- Receipt reactions, answer drafts, submission and cleanup across both interfaces.
- Per-chat exclusions and one selected interactive questionnaire chat.
- Notification history, delivery status and explicit recovery updates.

Telegramvisor uses unmodified T3 APIs and the existing MCPX Telegram bridge.

## Dashboard

The default dashboard is http://127.0.0.1:9038. History shows retained notification,
questionnaire and cleanup outcomes. Chats controls exclusions and the one interactive
questionnaire chat. Recovery can ask an eligible chat for a fresh assessment when
historical completion coverage is incomplete; currently one request per chat is
retained. A fresh answer does not reconstruct an old notification.

Run `telegramvisor auth forge` as the service account to obtain a single-use,
five-minute sign-in token. The browser receives an eight-hour session that survives
restarts until its original expiry or sign-out. Access is restricted to the loopback
origin and authenticated mutations require the current CSRF token.

## Running

Use Node 24 or newer. Run `npm ci`, `npm run build`, then `npm start`.
`telegramvisor start` is the installed CLI equivalent. Configure the service with
these environment variables; credentials are read from private files.

| Variable | Purpose |
| --- | --- |
| DATA_DIRECTORY | Persistent private state directory |
| T3_URL | Native T3 server address |
| T3_TOKEN_FILE | Private native orchestration read credential |
| T3_INPUT_TOKEN_FILE | Private native questionnaire response credential |
| T3_OPERATE_TOKEN_FILE | Private credential for explicit recovery messages |
| MCPX_URL | Existing Telegram bridge gateway |
| TELEGRAM_ENABLED | Opt-in master switch, default false |
| INPUT_ENABLED | Opt-in questionnaire relay, default false |
| HEALTH_PORT / UI_PORT | Defaults 9037 / 9038 |
| MANAGED_THREAD_IDS_FILE | Optional private inventory of existing service-owned chats |
| CX_HOME / CX_SEED_FILE | Private recap runtime login cache and seed |

The container requires the published recap runtime recorded in
`runtime-provenance.json`; `node scripts/fetch-runtime.mjs` verifies and fetches it.
The Compose template joins the existing MCPX network (default `lunar-mcpx_default`);
set `MCPX_NETWORK` for another deployment. It never creates a second Telegram router.
Health and liveness endpoints are `/health` and `/live` on port 9037.

Telegram and input are independently opt-in, with the master Telegram switch taking
precedence. Disabled workers retain their queues and uncertainty. Re-enabling resumes
existing queued work without treating all disabled-period completions as new work.

State lives under `DATA_DIRECTORY`: completion/catalog/outbox, native input, reply
cleanup, chat settings and private login/model state. Persist it across deployments.
Unknown sends or submissions are reconciled under their original identity, never
blindly resent. Only confirmed non-delivery follows the original-key retry path.

The optional managed-thread inventory contains only existing service-owned T3 thread
IDs. New `supervisor-root:` native IDs and descendants are excluded automatically.
A configured unavailable or malformed inventory fails closed.

## Development

Run `npm run autofix`, `npm run typecheck`, `npm test` and `npm run build`.
Keep credentials and runtime state out of Git and images. Native read evidence,
source checks and actual Telegram delivery are separate verification scopes.
